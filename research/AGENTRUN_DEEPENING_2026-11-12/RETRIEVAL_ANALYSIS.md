# Campaign 2 — Retrieval Analysis

## Setup

All retrieval experiments use Qwen2.5-7B-Instruct, v2 harness, memory scenarios only (S1–S4), configs B/D/E.

**Baseline:** hash256 retrieval with 7–12 records per memory store (no padding). This is the default AGENTRUN configuration.

**Scaled conditions:** Each memory store is padded with 2,000 background records (unrelated to the task) to test retrieval under realistic store sizes.

## Key findings

### 1. Hash retrieval fails at scale

When the memory store grows from ~10 to ~2,000 records, hash-based retrieval drops from 71.4% to 41.7% task success — a **29.7 pp decline** (p < 0.0001).

The root cause is recall degradation: gold-record recall drops from 1.00 to 0.76. Hash-based lookup works when stores are small (the hash prefix is likely unique), but with 2,000 records, hash collisions cause the agent to retrieve irrelevant records and miss the gold ones.

### 2. BM25 maintains performance at scale

BM25 retrieval with 2,000 background records achieves 70.3% success — essentially matching the small-store baseline (71.4%). Gold-record recall stays at 1.00. BM25's term-frequency matching correctly identifies the task-relevant records even among 2,000 distractors.

### 3. BM25 vs hash at 2,000 records

BM25 outperforms hash by **28.6 pp** at the same store size (p < 0.0001). This is the largest single-factor improvement measured in the retrieval experiments.

## Implications

1. **AGENTRUN's default hash retrieval is inadequate for production use.** Any deployment with more than a few dozen records will see significant recall degradation.

2. **BM25 is a minimum viable retriever.** It maintains perfect recall at 2,000 records with no additional infrastructure (no embedding model, no vector database). This should be the default.

3. **Dense retrieval remains untested.** The bge-small condition (job 14) was not completed. Dense retrieval would test whether learned semantic similarity can further improve recall or success rate compared to BM25.

4. **The interaction between retrieval quality and reliability components is important.** Config E (reliability gate) achieves 31/64 = 48.4% even with degraded hash retrieval (vs 56/64 = 87.5% with good retrieval). The gate cannot fully compensate for poor retrieval but provides partial protection.

## Limitations

- Only tested on Qwen2.5-7B. Larger models may be less sensitive to retrieval quality.
- Only tested with 2,000 background records. Real deployments may have orders of magnitude more.
- Background records are randomly sampled; adversarially confusing distractors could be harder.
- Only memory scenarios (S1–S4) tested. The effect on non-memory scenarios is structurally zero.
